# Scanner recovery integration: diagnostic only

The isolated app ID is `com.example.myebookapp.recovery20261122` (Foxlet: `com.example.myebookapp.foxlet.recovery20261122`). It has not been built or installed. Existing installs and original ebook/provider files were not changed. Folder addition and all folder-removal/restore UI remain disabled. No boot receiver was added.

V3 Room staging records the entire pre-add logical queue, mode and unique preference revision, the new root and the inventory generation in the same transaction. The actual scanner's visible-UI restore and worker reconciliation invoke V3 replay under the processing mutex, and queue checkpoint changes are compared and written under the scanner lock. A completed replay becomes paused or interrupted, never starts scanning. Explicit stop after staging wins; a later pause stays paused; unmatched revisions and ambiguous ADD/V2 journals fail closed with their journal retained. Room finish checks the expected journal, roots and generation. Process-local preference values are recommitted before a previously written marker or stop is accepted. Service-owner and timeout start-ID checks limit stale lifecycle callbacks. Recovery does not write to ebook/provider files.

**Not a completed feature:** no production path invokes V3 staging; Add Folder is deliberately still hard-disabled. Consequently V3 integration can currently be exercised only by tests or diagnostic database injection, not by normal users. This avoids claiming safe addition before grant acquisition, foreground service failure, exact admission ordering, failure and lifecycle races are verified. The pre-existing V2 replay lab remains unwired. V3 recovery can leave changed folder preferences and a retained journal after a failed later checkpoint; that is intentional for retry, but this is not cross-store all-or-nothing visibility. Unexpected revisions fail closed instead of merging arbitrary controls. Old journals need a separate safe repair path. A failed SharedPreferences commit can update memory even when disk persistence failed; the recommit mitigation requires real device fault testing. Other database writers and the entire SAF/provider behavior remain unaudited for production. The owner check does not prove all same-service or asynchronous foreground-start failure races are safe. No claim that a stop or pause with a failed commit is durable.

Tests: host checks include SQLite rollback models and source contracts, not Kotlin execution. Android instrumentation exercises actual Room/preferences staging/replay, failure on Room finish, a simulated false preference commit, idempotent retry, stop and stale-owner examples; these are unrun, do not kill a process, and do not inject real preference disk failure, all callbacks or SAF I/O. Android SDK/Java/Gradle are unavailable here. Before activation: compile and run instrumentation; kill/restart at every Room and preference boundary; inject preference and Room failures and grant revocation; race startup, pause/stop/resume/enqueue, service starts/destroys/timeouts and blocking provider reads; audit inventory-generation writers; verify permissions, foreground restrictions, migration and UI error/recovery behavior. Full scanner safety and crash recovery are not proven.
