# Whole-root detach backend experiment — NOT ready to expose

This isolated copy implements only a reversible **scan configuration detach**. It does NOT remove or hide any book from the library, and therefore does not yet meet the requested folder-removal behavior. No UI calls these APIs. It never deletes/moves ebook files or releases a persistable grant. All existing book rows, shelves, metadata, conversion links and legacy/unknown/shared data stay untouched. The detach API's return value is the total library row count, not an affected count.

`LibraryScanner.detachWholeScanRoot` and `restoreDetachedScanRoot` use the service worker's admission lock, interrupt/cancel the worker, then acquire its processing mutex, including its non-cancellable metadata cleanup. Room v10 stores a `removed_scan_roots` tombstone before saved preferences or the journal are changed. Scanner walks and the transactional batch insert both consult tombstones, so a stale queue or a parent traversal through the exact same opaque directory ID cannot insert through that route after commit. A separately configured root with the same directory ID but a different grant remains eligible. Matching is scoped to provider authority, never a path-prefix comparison. Restore saves the preference before clearing the tombstone and does not start a scan.

This is not a provider ownership proof. Provider aliases, moved documents, or alternate routes bypassing the removed directory can still be scanned; existing shared memberships are retained. A crash or preferences-write failure may leave the tombstone committed while the old preference or queue is still present; the scanner remains blocked for the exact removed route, but the UI might display a stale root. A retryable reconciliation and clear partial-success reporting are needed. Similarly, existing `addFolder` does not clear a tombstone; explicit restoration/re-add UX and grant validation are not integrated. An excluded exact directory in a parent is suppressed even if users wanted that parent route separately; the intended UX and root-scoped override policy need review. No guarantee is claimed for provider or other process changes.

No library visibility implementation has been attempted because current old scanner origins and historical routes cannot establish absence of manual/legacy/shared associations. A possible forward path is explicit app-owned membership tracking for newly indexed entries, capture independent/manual associations, protect metadata in intact rows, and implement reversible visibility consistently across search, paging, counts, shelves, bulk actions, reader and conversion. Consider fail-open on unknown association and specify alternative-grant behavior; do not infer ownership from a purported provider lease. Existing older rows must remain visible when ownership is uncertain.

Room migration and Android tests are written but have not run. The inherited v9 migration/index compatibility problem is still unresolved. The v5–v9 instrumented fixtures are reconstructed, not independent historical schemas. No Android build, real device, SAF provider, service concurrency, process-death recovery or grant test has run. Host tests exercise SQLite/source contracts only and are not proof of runtime safety. Keep this experimental code out of production and UI until those blockers and the missing visibility behavior are resolved.
